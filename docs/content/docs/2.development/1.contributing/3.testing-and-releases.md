## Testing

Tests use Bun's built-in runner and live **next to the source** they cover as `*.test.ts`:

```bash [Terminal]
bun run test
```

When you add behavior, add a `*.test.ts` beside it. Coverage runs with `bun run test:coverage`.

Plugin authors have a dedicated testing kit. See [Plugin development → Testing](/docs/development/plugins/testing).

## Commits and releases

Releases run on [Changesets](https://github.com/changesets/changesets). You never bump a version or edit a changelog by hand.

Add a changeset in any PR that changes published behavior:

```bash [Terminal]
bun run changeset
```

It asks which packages changed and at what bump level, then writes a markdown file to `.changeset/`. Commit that file with your work. Docs-only or internal changes that ship nothing to npm don't need one.

On merge to `main`, CI opens (or updates) a **Version PR** that applies every pending changeset: bumping versions, rewriting changelogs, and syncing the lockfile. Merging that PR publishes to npm and tags the release.

::note
Version PRs are created by `GITHUB_TOKEN`, which does not trigger CI runs. If you need checks on one, close and reopen it.
::

Write commit messages with [Conventional Commits](https://www.conventionalcommits.org/) prefixes. Versioning comes from changesets, not from the commit type.

::note
CI runs the same `bun run check` and `bun run test` you run locally, so a green local run should mean a green pipeline.
::
