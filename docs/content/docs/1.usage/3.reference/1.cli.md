The `fakeware` binary has five commands: `init`, `up`, `down`, `status`, and `validate`. This page documents each one exactly.

## Global options

Available on the root command and inherited by every subcommand:

::field-group
  :::field{name="-V, --version"}
  Print the version and exit.
  :::

  :::field{name="--no-color"}
  Disable ANSI colors in output. Also honored via the `NO_COLOR` environment variable.
  :::

  :::field{name="--verbose"}
  Show debug logs and full stack traces. Without it, unexpected errors print a single readable line and suggest re-running with `--verbose`.
  :::

  :::field{name="-h, --help"}
  Show help. Available on every command.
  :::
::

```bash [Terminal]
fakeware --help
fakeware up --help
```

## Exit codes

Every command uses the same convention.

::field-group
  :::field{name="0"}
  Success. Also used when there is legitimately nothing to do: no manifest to revert, no data files to apply, or a validation that only needs the shop.
  :::

  :::field{name="1"}
  Failure. A run was stopped, the API or config rejected something, validation found problems, or `down` could not remove every record.
  :::

  :::field{name="2"}
  Usage error. An unknown flag, or an invalid value for a constrained option such as `--secrets` or `--template`.
  :::

  :::field{name="130"}
  Cancelled by the user, either with `Ctrl+C` or by declining a confirmation prompt.
  :::
::

## `fakeware init`

Scaffold a project (a `package.json`, a typed `fakeware.config.ts`, an `.env`, and an example `data/products.ts`) or a plugin, then install dependencies. The project template is the same routine `create-fakeware` runs.

```bash [Terminal]
fakeware init [options]
```

### Options

::field-group
  :::field{name="--template &lt;kind&gt;" type="project | plugin"}
  What to scaffold. `project` (the default) creates a data project. `plugin` creates a Fakeware plugin package with a fetcher, a hook, and a test.
  :::

  :::field{name="--url &lt;url&gt;"}
  Shopware URL to pre-fill the connection.
  :::

  :::field{name="--client-id &lt;id&gt;"}
  OAuth2 client ID.
  :::

  :::field{name="--client-secret &lt;secret&gt;"}
  OAuth2 client secret.
  :::

  :::field{name="--output &lt;path&gt;"}
  Directory to scaffold into. Defaults to the current directory.
  :::

  :::field{name="--secrets &lt;dest&gt;" type="env | inline"}
  Where to put credentials: a git-ignored `.env` (`env`, the default) or written directly into the config (`inline`).
  :::

  :::field{name="--package-manager &lt;pm&gt;" type="bun | npm | pnpm | yarn"}
  Which package manager to use. Auto-detected if omitted.
  :::

  :::field{name="--plugins &lt;list&gt;"}
  Official plugin ids to add, comma-separated. Also accepts `all` or `none`. Adds the dependency and injects the import plus a `plugins[]` entry into the generated config.
  :::

  :::field{name="--no-plugins"}
  Do not add any official plugins.
  :::

  :::field{name="--no-example-data"}
  Do not scaffold the example `data/products.ts` file.
  :::

  :::field{name="--no-install"}
  Write files but skip installing dependencies.
  :::

  :::field{name="--force"}
  Overwrite existing files in a non-empty directory.
  :::

  :::field{name="--dry-run"}
  Preview the files that would be written without writing them.
  :::

  :::field{name="--yes"}
  Accept defaults and never prompt. Use for non-interactive runs.
  :::
::

### Interactive vs. non-interactive

`init` is interactive by default, walking you through location, package manager, official plugins, and optionally connecting to your shop (validating the connection before writing).

It runs **non-interactively** when the terminal isn't a TTY, when you pass `--yes`, or when you supply `--url`, `--client-id` and `--client-secret` together. In that mode it uses defaults and prompts for nothing, which is ideal for CI.

```bash [Terminal]
fakeware init \
  --url https://my-shop.example.com \
  --client-id "$SHOPWARE_CLIENT_ID" \
  --client-secret "$SHOPWARE_CLIENT_SECRET" \
  --yes
```

## `fakeware up`

Apply your data definitions to the shop.

```bash [Terminal]
fakeware up [options]
```

### Options

::field-group
  :::field{name="--config &lt;path&gt;"}
  Path to `fakeware.config.ts`. Defaults to searching the current directory and its parents.
  :::

  :::field{name="--dry-run"}
  Resolve and diff everything, report what would change, but write nothing and don't touch the manifest.
  :::

  :::field{name="--verbose"}
  Show debug logs, including per-request detail and retry attempts.
  :::
::

### Output

`up` reports per-entity progress with created / updated / unchanged counts, then a summary:

```text
Committed 210 changes to https://my-shop.example.com
```

The other endings are all deliberate and distinct:

- `No data files found in ./data. Add one to describe what to create.` when the project has no data files at all.
- `Dry run complete. Nothing was written.` after `--dry-run`.
- `Already up to date. Nothing changed.` when the shop already matches your definitions.

## `fakeware down`

Delete the demo data Fakeware created, per its manifest.

```bash [Terminal]
fakeware down [options]
```

### Options

::field-group
  :::field{name="--config &lt;path&gt;"}
  Path to `fakeware.config.ts`. Same resolution as `up`.
  :::

  :::field{name="--yes"}
  Skip the confirmation prompt. Required for non-interactive teardown.
  :::

  :::field{name="--dry-run"}
  Report what would be deleted without deleting anything or touching the manifest.
  :::

  :::field{name="--verbose"}
  Show debug logs and full stack traces.
  :::
::

### Behavior

`down` first reads the manifest for the configured shop. If there's no manifest, it's a friendly no-op (`Nothing to revert. No fakeware manifest found.`). Otherwise it shows how many records will be removed and, unless `--yes` is given, asks you to confirm. Declining exits `130`.

It deletes in reverse dependency order across multiple passes to tolerate Shopware delete conflicts (see [Up and down](/docs/usage/concepts/up-and-down)). On success:

```text
Removed 210 records from https://my-shop.example.com
```

If some entities could not be removed, they are named, kept in the manifest, and the command exits `1`. Run `down` again once the blocker clears: the manifest is a ledger, so a repeated run converges.

## `fakeware status`

Show what Fakeware has applied to the shop, read entirely from the local manifest. Makes no network calls.

```bash [Terminal]
fakeware status [options]
```

### Options

::field-group
  :::field{name="--config &lt;path&gt;"}
  Path to `fakeware.config.ts`. Same resolution as `up`.
  :::

  :::field{name="--json"}
  Print the report as JSON on stdout, with no decoration. Use this in scripts.
  :::
::

### Output

Without a manifest, `status` reports that nothing has been applied yet and exits `0`. With one, it prints the shop URL, the config path, any configured plugins, when the data was applied and by which Fakeware version, followed by a per-entity record count. Entities left in a `pending` state from an interrupted run are flagged.

The `--json` output is the same data, unstyled, and is the stable shape to script against.

## `fakeware validate`

Check your config and data files for errors without contacting the shop. Useful as a fast pre-commit or CI gate.

```bash [Terminal]
fakeware validate [options]
```

### Options

::field-group
  :::field{name="--config &lt;path&gt;"}
  Path to `fakeware.config.ts`. Same resolution as `up`.
  :::
::

### Behavior

`validate` loads your config, discovers `data/`, evaluates every data file, and builds the write plan against a placeholder shop context. It reports a checklist of four checks: data files, definitions, references, and the dependency graph. A failing check names the problem and short-circuits the checks after it, since they cannot be trusted once an earlier stage failed.

Because it never contacts the shop, code that reads live shop values (`shop.context()`, plugin extensions) cannot be resolved offline. When your data depends on such values, `validate` marks the reference and graph checks as needing the shop, explains why, and still exits `0`. That is not a failure: those values are checked for real on `fakeware up`.

Exits `1` only when your project is genuinely broken, for example an unresolvable `ref(...)` or a cycle in the dependency graph.

## Configuration resolution

All commands except `init` locate the config the same way: use `--config` if given, otherwise search the current directory and walk up the tree for `fakeware.config.ts`. The directory containing the config is the project root, which anchors `data/` and `.fakeware/`. Details are in the [Configuration reference](/docs/usage/reference/configuration).
